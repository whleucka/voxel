# Implementation Plan: items

Spec: [SPEC-items.md](../SPEC-items.md) · Map: [CAPABILITY_MAP.md](../CAPABILITY_MAP.md)
Tasks: [items-todo.md](items-todo.md)

## Overview

Add item definitions, a drop table and stack logic as a pure-logic module
under `inc/item/` and `src/item/`, plus a placeholder item-icon atlas. No
gameplay or rendering changes. `Engine` and `Game` are untouched.

## Architecture Decisions

- **`ItemId` 1..255 are a cast from `BlockType`,** so block items need no
  table entries and new blocks automatically become items. The 7 materials
  start at 256.
- **Block item definitions are built on demand** from `blockName()` and
  `block_data`, and returned from a lazily built table. That way
  `itemDef()` can return a stable reference.
- **Normalized stacks:** an empty stack is always `{NONE, 0}`, and
  `mergeInto`/`split` keep that true.
- **The placeholder atlas is generated by a committed script** that is
  deterministic (fixed shapes and colours, no randomness), so rerunning it
  produces a pixel-identical PNG. The existing `resources` Makefile target
  already copies everything in `res/` to `bin/`.

## Dependency Graph

```
T1 ItemId + definitions
 ├─ T2 drop table
 ├─ T3 ItemStack logic
 └─ T4 placeholder item atlas (tile coords come from T1)
     └─ T5 wrap-up
```

T2, T3 and T4 are independent once T1 exists, but each is small, so I'll do
them in order.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| A future `BlockType` above 255 breaks the "block IDs are a cast" rule | Low | `static_assert` that `BlockType` fits in `uint8_t`. It already does, since its underlying type is `uint8_t`. |
| `block_data` is a `static` map in a header, so every translation unit gets its own copy | Low | Only read it from `item.cpp`. Nothing new depends on cross-TU identity. |
| Pillow is missing on someone's machine | Low | The script is only for regenerating art. The PNG is committed and the build never runs the script. |
